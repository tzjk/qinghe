## 结论

本轮仅完成静态审计与设计。现有 `qh_student_profile`、`qh_dorm_checkin`、`qh_asset_set`、`qh_asset`、`qh_dorm_bed`、`qh_admin` 和唯一 `qh_operate_log` 已能承载单个学籍异动、退宿联动、二维码安全操作，以及受限的原子批量毕业/退宿；本轮不需要新增或执行数据库迁移。

唯一必须在后续实施中纠正的契约漂移是：旧基础 SQL 和 `StudentDormServiceImpl` 把 `TRANSFER_MAJOR`、`REINSTATED` 当作当前 `student_status`。本设计将二者收敛为异动类型；当前状态只使用 `ENROLLED`、`SUSPENDED`、`DROPPED`、`GRADUATED`。这样转专业和复学不会成为永久状态，也不会放宽非在籍学生的扫码入住门禁。

## 已核实的模型与边界

| 对象 | 已有能力 | 本设计的不可改变语义 |
|---|---|---|
| `qh_student_profile` | 资料版本、状态、生效/失效时间、异动原因、管理员、当前版本唯一键 | `current_flag=1` 是唯一当前资料；历史行必须设为 `NULL`，绝不改作启停或学籍状态。 |
| `qh_dorm_checkin` | 有效入住唯一键、学籍/位置快照、退宿时间/原因、管理员、历史关联 | `active_flag=1` 是唯一当前入住；关闭时写 `NULL`，不物理删除。 |
| `qh_dorm_bed` | 床位目录与启停状态 | `status` 只代表目录启停，绝不表示占用、毕业或退宿。 |
| `qh_asset_set` / `qh_asset` | 套装状态、二维码令牌/启停/轮换时间、五项资产和健康状态 | 套装编号不改写；不清空二维码令牌；有当前入住时不得强制释放。 |
| `qh_admin` / `AdminContext` | 单一管理员会话和 `/api/admin/**` 拦截 | 当前没有角色表；所有本设计的写操作继续使用统一管理员身份。 |
| `qh_operate_log` | 已有 AOP 安全摘要日志 | 不新建业务日志表；摘要不得含完整姓名、学号、手机号或二维码令牌。 |

## 统一学籍状态与版本规则

| 当前 `student_status` | 含义 | 可扫码入住 | 宿舍约束 |
|---|---|---:|---|
| `ENROLLED` | 在籍 | 是 | 可以存在一条当前入住。 |
| `SUSPENDED` | 休学 | 否 | 可由管理员选择保留当前入住或在同一业务请求中退宿。 |
| `DROPPED` | 退学 | 否 | 不得存在当前入住；状态变更与退宿必须原子完成。 |
| `GRADUATED` | 毕业 | 否 | 不得存在当前入住；状态变更与退宿必须原子完成。 |

- `TRANSFER_MAJOR` 是异动类型，不是当前状态。完成后新当前资料仍为 `ENROLLED`。
- `REINSTATED` 是异动类型，不是当前状态。完成后新当前资料仍为 `ENROLLED`。
- 每一次管理员学籍变更均关闭旧当前资料（`end_time=effectiveTime`、`current_flag=NULL`），新建一条资料副本为当前版本；副本只改变该异动允许变更的字段，并写入 `effective_time`、`change_reason`、`operator_admin_id`。
- 当前资料的学号、用户、校区、实名和联系电话不是本轮异动的可修改范围。普通学生只保留既有的资料初建/联系电话维护边界，不得调用管理员学籍接口。

## 单个学籍异动规则

### 转专业

仅在管理员身份下办理。关闭旧版本后新建当前版本；只改变 `college_name`、`major_name`、`class_name`，`student_status` 保持 `ENROLLED`。必须填写原因与生效时间，保留原版本。不自动退宿，不新建或关闭入住记录，当前床位和资产套装关系不变。

### 休学与复学

休学新版本为 `SUSPENDED`，管理员必须明确选择以下一种策略：

1. `KEEP_DORM`：仅变更学籍，保留现有入住；该学生不能再扫码新入住，也不得被换寝接口自动迁移。
2. `CHECKOUT_DORM`：学籍版本变更与既有单个退宿事务在同一事务中执行。关闭当前入住、写入退宿时间/原因、释放原资产套装为 `AVAILABLE`，床位目录状态不变。

复学新版本为 `ENROLLED`，不恢复旧 `qh_dorm_checkin`，不恢复旧床位，不占用旧资产套装。学生须重新扫码入住，或由管理员通过既有分配/换寝能力创建新的当前入住。旧入住及其关联的旧学籍版本只作历史查询。

### 退学与毕业

退学创建 `DROPPED` 当前版本，毕业创建 `GRADUATED` 当前版本。两者都必须在一个事务内完成：锁定当前资料和当前入住；关闭当前入住；记录退宿时间、原因和管理员；将该入住绑定的资产套装由 `OCCUPIED` 恢复为 `AVAILABLE`；再提交新当前学籍版本。若没有当前入住，只完成版本变更。任何一步失败均回滚，不允许留下“已毕业/退学但仍有效入住”或“入住已关闭但学籍未改变”的中间状态。

学生账号、全部学籍版本、入住历史、床位目录和资产历史均保留，均不物理删除。

## 学籍与宿舍联动实现准则

- 后续抽取并复用现有 `AdminDormCheckinServiceImpl` 的“锁定有效入住 → 关闭记录 → 释放套装”事务内核；不得另写直接 `UPDATE qh_asset_set` 的旁路。
- 入住校验只能接受当前资料为 `ENROLLED`。现有允许集合中的 `TRANSFER_MAJOR` 与 `REINSTATED` 必须移除；`SUSPENDED`、`DROPPED`、`GRADUATED` 都不得新增入住。
- 入住记录绑定办理当时的 `student_profile_id` 并保存学籍快照，所以转专业、休学、复学后不会改写历史入住含义。
- 退宿原因使用明确业务前缀和人工原因，例如“毕业处理：{原因}”；存入 `checkout_reason`，日志仅保存脱敏摘要和操作类型。

## 管理员权限与审计

当前 `qh_admin` 只有账号、密码哈希、显示名和启停状态，没有角色/权限表。因此本阶段的学籍查询、单个异动、单个退宿/换寝、批量毕业、批量退宿、批量资产释放、二维码停用/启用/轮换均使用现有 `AdminContext` 与 `/api/admin/**` 拦截保护；普通用户 Token 一律不得访问。

每个写入口均使用既有 `@OperateLog`，复用唯一 `qh_operate_log`。日志可记录操作类型、内部范围引用、数量、成功/失败计数和脱敏原因摘要；不得记录完整姓名、学号、手机号、`qrToken`、二维码原文或完整候选名单。不得新增 `academic_log`、`graduation_log`、`dorm_clear_log` 或 `qr_clear_log`。未来需要教务、宿管、资产管理员细分权限时，再经单独审批设计 RBAC；不得在本轮伪造不完整角色判断。

## 管理员批量操作边界

### 批量退宿

输入必须是预览后固定的当前入住范围及必填原因，而不是“清空二维码信息”。逐条锁定仍为 `active_flag=1` 的入住，复用退宿事务关闭记录并释放其绑定套装。历史记录、二维码令牌、床位目录都不删除或改写。

### 批量释放资产

仅允许预览到不存在当前入住的套装。`AVAILABLE` 为幂等跳过；`OCCUPIED` 且仍有当前入住必须拒绝；`OCCUPIED` 但无当前入住只能作为显式“入住一致性修复”处理，并记录原因；`MAINTENANCE`、`RETIRED` 不因批量释放恢复可用。不得使用无条件全表状态更新。

### 二维码停用、启用与轮换

- 停用：只把 `qr_status` 置为停用；不删除、不置空 `qr_token`，不改历史入住。可用于遗失、泄露或盘点场景，且不等同于退宿或资产释放。
- 启用：仅针对启用目录、资产健康、套装 `AVAILABLE` 且无当前入住的套装；只恢复 `qr_status`，不生成新令牌。
- 轮换：仅针对空闲、无当前入住且可用的资产套装。使用既有 `SecureRandom` 生成新的唯一 64 位十六进制令牌，原子更新 `qr_token` 与 `qr_rotated_time`；旧二维码立即无法解析，不修改 `asset_set_no`。轮换日志不记录新旧令牌。
- 不允许对存在当前入住的套装轮换二维码，也不以轮换或停用绕过资产套装的 `OCCUPIED` 约束。

## 批量毕业：预览、确认、事务与恢复

第一版采用**受上限的单事务批处理**，推荐每次不超过 100 名学生。它避免了持久化半完成任务所需的新表，也满足本轮“继续复用唯一操作日志”的限制。

1. 管理员按毕业学年、学院、专业、班级筛选当前 `ENROLLED` 资料；服务端返回脱敏名单、总人数、当前入住人数、不可处理项和范围摘要。
2. 管理员进行二次确认，提交预览引用、同一筛选摘要、原因和毕业生效时间。服务端必须重新核对当前版本/状态和入住状态；范围或版本变化返回冲突，要求重新预览。
3. 事务内按稳定 ID 顺序锁定学生当前资料、当前入住、资产套装；逐名创建 `GRADUATED` 当前版本，并对存在入住者复用关闭与释放内核。
4. 任一学生不满足前置条件、并发状态变化或资产更新失败时，整批回滚。结果不是“部分成功”，管理员修复问题后重新预览并重试；这就是明确的恢复方案。
5. 成功后可由新学籍版本的 `operator_admin_id/effective_time/change_reason`、关闭入住的 `operator_admin_id/checkout_time/checkout_reason` 和 `qh_operate_log` 的批次摘要追溯每名已处理学生。查询和响应仅显示脱敏学号。

若将来需要超过该上限的异步、分片、可暂停批处理，现有表无法可靠持久化“候选、每项状态、失败原因、重试次数”。那是独立的数据模型决策，必须先获得单独授权；本轮不以伪造日志表或无条件更新替代它。

## 数据库迁移评估

本轮结论为**不生成、不执行增量 SQL**：现有 `VARCHAR(16)` 可容纳四个统一状态；学籍版本、退宿、资产释放、二维码启停和轮换所需字段/索引已经存在。后续实施前只需将基础设计文档、状态校验常量和测试数据统一为 `DROPPED`，不再写入 `DROPPED_OUT`、`TRANSFER_MAJOR`、`REINSTATED`。

不建议现在添加数据库 `CHECK` 约束或强制数据修复，因为本轮未读取线上历史状态分布；若未来发现旧值，必须先只读盘点、定义历史兼容策略，再由授权人员审查独立迁移。也不建议以新增日志表解决批处理追踪。

## 推荐实施顺序

1. **阶段一：管理员学生资料与学籍查询**：在现有管理员门禁中新增当前/历史资料查询和脱敏视图，只读验证学籍版本、入住和资产关联。
2. **阶段二：单个转专业与学籍状态变更**：实现统一状态常量、版本复制/关闭内核、管理员原因与生效时间；转专业不退宿。
3. **阶段三：休学、退学、毕业联动退宿**：实现休学两种明确策略，以及退学/毕业的原子状态变更、退宿和资产释放；补足回滚/并发测试。
4. **阶段四：复学和重新入住**：复学仅恢复 `ENROLLED`，不恢复旧入住；沿用现有扫码或管理员重新分配。
5. **阶段五：批量毕业与批量退宿**：先实现预览、二次确认、100 人上限、稳定锁顺序和全回滚；不得无条件全表更新。
6. **阶段六：二维码批量停用和安全轮换**：实现套装预览、停用/启用/轮换的前置条件、`SecureRandom` 新令牌和安全日志；不清空令牌。
7. **阶段七：统计与异常恢复**：只读一致性报表、失败重试入口、异常状态人工复核；大批量异步化另行审批数据模型。
