## 模块核对

### 1. 商铺与商品

- 用户端商铺接口为 `GET /api/shops`、`GET /api/shops/{id}`、`GET /api/shops/{id}/goods`、`GET /api/shops/{id}/comments`；页面通过 `frontend/src/api/shop.js` 调用。
- 商品公开接口为 `GET /api/goods`、`GET /api/goods/{id}`；`GoodsService` 仅检查商品上架状态，未校验所属商铺状态。店铺内商品查询会先校验商铺启用。
- 资料字段目前仅有商铺分类、名称、地址、电话、评分、启用/推荐、排序和封面；商品仅有名称、描述、价格、库存、销量、上下架和封面。若“完整资料”包含营业时间、配送范围、配送费、起送价、公告或商品规格，需要另行确认产品字段和迁移，不应在本轮猜测性扩表。
- 后台的 CRUD/状态接口只出现在 `docs/api-contract.md`，不是已实现功能。

### 2. 购物车

- `CartServiceImpl` 在加购、原子累加和改数量时均重新读取商品和商铺：拒绝不存在商品、`OFF_SALE` 商品、停用商铺、超库存和非本人购物车项；Mapper 的 `INSERT ... SELECT` / `UPDATE ... JOIN` 同样带商品状态、商铺状态和库存条件。
- 商品价格没有持久化到 `qh_cart`，汇总与行项目从当前 `qh_goods.price` 计算。这适合购物车展示；订单创建必须重新锁定/读取当前价格并把价格写入 `qh_order_item.goods_price`，不能把购物车金额当订单金额。
- 购物车可按 `shop_id` 分组，前端已阻止多店同时结算；订单未实现，所以结算按钮只提示“建设中”，没有误调订单接口。
- 风险：查询时缺失商品或商铺的购物车行被静默跳过，既不提示也不清理；后续订单创建应明确处理失效行，而不是按静默跳过后的金额下单。

### 3. 订单与优惠券

- `qh_order` 已有订单号、用户/商铺/地址 ID、收件人和电话快照、可读配送地址快照、商品总额、优惠额、应付额、状态、备注及索引；`qh_order_item` 已有商品名称/图片/价格快照、数量和小计。它们足以承载基础订单行，但当前没有业务写入链路。
- 校园地址模型要求订单创建时保存不可变完整配送快照。当前只有 `delivery_address` 字符串；若订单需要按校区/楼栋/配送点查询或配送规则，须增加经审核的结构化 `delivery_snapshot`，不能在订单详情实时回读可编辑地址。
- `qh_coupon` 已有库存、领取数、状态、有效期、门槛和优惠额；`qh_user_coupon` 有用户券状态、订单 ID、领取/使用时间，以及 `(user_id, coupon_id)` 唯一约束。表模型可支持基础领取和单券防重复，但没有原子扣库存、有效期/门槛校验、下单占用与核销事务，故不能视为真实可用。

### 4. 校园配送

- 现有能力仅是校园地址中的 `campus_id`、`building_id`、`room_no`、`delivery_point` 与可读快照。
- 缺少可配置校区服务范围、配送点目录/规则、配送费、配送方式、配送员/配送状态和状态流转；`qh_order.status` 不能代替配送状态。
- 本轮未执行 `SHOW COLUMNS`、`SHOW INDEX` 或数据查询，因此上述表结论是仓库 SQL/实体映射结论，不代表真实 `qinghe_life` 实例已经同步。

## 店铺与商品图片专项评估

### 现状与结论

- 应复用现有 `AliyunOSSOperator` 和同一个 `aliyun.oss.bucket-name`，不创建第二个 OSS 客户端、第二个 Bucket 配置或平行上传栈。
- `cover_image VARCHAR(255)` 已能保存一张完整 OSS URL；在“店铺一张封面、商品一张主图”的范围内不需要数据库迁移。
- 已有头像路径为 `qinghe-life-service/{yyyy}/{MM}/{uuid}.webp`，但其旧图删除校验只识别头像路径。店铺和商品不能直接复用 `ownAvatarKey`，必须增加按资源类型严格校验 Bucket 主机名和前缀的安全 key 解析。

- 仓库只有 Spring Data Redis 和商铺详情缓存，未发现 Redisson、RabbitMQ、Kafka 或 Redis Stream 实现。后续优先 Redis Stream；当前手写商铺缓存锁缺所有者令牌校验，只能作为缓存重建整改对象。
