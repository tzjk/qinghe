# 10. Redis专项审计：优先级修复路线与执行计划

## 本轮审计边界

- 范围：`backend/` 与 `agent-service/` 的 Redis、缓存一致性、分布式锁、Lua 秒杀、Redis Stream、订单超时、热榜/GEO、Token 与 Agent 扩展性。
- 方法：读取实际源码、配置、Lua、SQL、测试与相关文档；逐项记录类、方法、Key、数据结构、TTL、事务/失败边界和代码证据。
- 禁止：修改任何业务代码或配置，执行 SQL，写入/删除 Redis Key，连接或控制 Redis、MySQL、Spring Boot、FastAPI，真实订单/秒杀操作及任何 Git 操作。
- 输出：仅创建 `docs/redis-audit/` 中用户指定的 12 份 Markdown；既有 `progress.md`、`findings.md` 和根 `task_plan.md` 仅作项目规则要求的记录，不创建其他审计文件。

## 2026-07-31 Phase R1 实施状态

- 已实施 Lua 预检、reservation、XADD 条件回滚、DLQ 去重写入、指数退避、每消息 retry TTL、Pending idle/批次限制、watchdog 锁、会话最小化、namespace 与轻量业务指标。
- 未实施自动 DLQ 回放、自动 Stream 裁剪、Redis 延迟队列、消息队列替换或数据库 DDL；真实 Redis/MySQL 验证仍待单独授权。

## 监控、告警与基准（R5/R6）

- Spring Actuator/Micrometer：Redis 连接/命令池指标；业务自定义缓存命中、空值命中、重建、失效失败、降级次数、锁等待/失败。
- Redis 服务端：内存、慢日志、命令延迟、客户端、Keyspace、Stream 长度、Pending、最老 Pending、消费速率、死信数。
- 日志：只记录 Key 类型/长度/哈希化标识，禁止 Token、手机号、实名、学号和完整消息。
- 基准：目录缓存命中/回退、每店商品量、热榜/GEO、锁 P99、秒杀 Pending/恢复；仅在隔离环境，不能伪造生产结果。

## 预定修复路线（本轮仅设计）

### Phase R0：现有实现证据确认

- 修改模块：无（只读审计）。
- 数据库/Key：不修改。
- 兼容与回滚：无运行时变化。
- 测试：只运行不访问外部服务的静态检查；不启动应用或连接中间件。
- 验收：使用矩阵的每一行均能定位到实际文件、类和方法，缺失项显式标记“未实现”。

### Phase R1：P0/P1正确性修复

- 修改模块：待 R0 取证后限定在具体服务、Lua、消费端或拦截器。
- 数据库：仅当现有唯一约束/条件更新无法成为最终幂等兜底时，生成供人工审核的增量 SQL；本轮不生成或执行 SQL。
- Redis Key：优先保留现有规范；仅在真实冲突、泄露或不可运维时迁移。
- 兼容风险：Token、秒杀库存、消费者组与锁 Key 的双写/切换需要可回滚窗口。
- 测试：离线单元测试 + 受控的后续集成测试；覆盖 ACK 丢失、重复消息、锁失效、Redis 故障。
- 回滚：保留数据库最终约束和原同步路径，按功能开关或版本化消费者回退。
- 验收：不存在可证明的超卖、重复订单、事务提交前不可逆缓存破坏或锁误释放。

### Phase R2：缓存一致性和失效补全

- 修改模块：待取证后仅限缓存读取/写入服务及对应更新接口。
- 数据库：通常不修改；以事务提交后失效、清晰的 Cache Aside 边界为先。
- Redis Key：可能补充空值/重建锁/版本 Key；不默认引入延迟双删、CDC 或多级缓存。
- 兼容风险：缓存 TTL 与序列化变更需要灰度或兼容读取。
- 测试：事务回滚、并发读写、空值、热点失效、Redis 不可用和序列化兼容测试。
- 回滚：停用新增缓存路径并回退数据库读取；不得以缓存作为唯一事实源。
- 验收：所有会改变缓存对象的写接口都有可解释失效策略，且事务顺序正确。

### Phase R3：Redis Stream Pending/重试/死信

- 修改模块：待取证后限定于秒杀 Lua、Stream 初始化、消费者和恢复任务。
- 数据库：优先使用既有唯一索引/状态条件更新；缺口才提出人工审核 DDL。
- Redis Key：可新增有 TTL 或明确保留期的重试/死信/消费状态 Key；Stream 剪裁须有数据保留规则。
- 兼容风险：消费组名称、消息字段与消费者接管策略需要向后兼容。
- 测试：消费者宕机、ACK 丢失、DB 失败、毒消息、堆积和服务重启恢复。
- 回滚：保留 Pending 消息和旧组；禁止直接丢弃未确认消息。
- 验收：达到至少一次投递、提交后 ACK、Pending 接管、幂等、有限重试、死信和积压监控的明确标准。

### Phase R4：锁粒度和幂等优化

- 修改模块：仅真实存在且无法由数据库唯一约束、原子 UPDATE、Lua 或状态条件更新替代的锁点。
- 数据库：优先约束、乐观锁和条件更新作最终保障。
- Redis Key：锁 Key 按业务实体细分并包含环境/模块边界；避免全局锁。
- 兼容风险：lease/watchdog 策略不当会改变并发特征，需压测验证。
- 测试：多实例竞争、锁获取失败、租约超时、异常 finally、事务边界与 Redis 故障。
- 回滚：删除新增锁前先确认数据库幂等保护仍可覆盖。
- 验收：无锁误删、失败后继续执行或在锁内做慢外部调用；锁只保护必要临界区。

### Phase R5：监控、告警和故障降级

- 修改模块：指标配置、业务埋点和受控降级层；不以日志泄露 Token 或个人信息。
- 数据库/Key：不作为常规修改项。
- 兼容风险：指标标签基数、日志量和降级开关需受控。
- 测试：Redis 连接/命令超时、热点、缓存重建、Pending 堆积与功能快速失败策略。
- 回滚：关闭自定义埋点或降级开关，不影响数据库事实路径。
- 验收：能区分 Actuator/Micrometer、Redis 服务端、业务指标和日志指标，并能告警关键不可用/堆积状态。

### Phase R6：性能基准与简历数据

- 修改模块：仅基准脚本、监控面板与文档；不伪造压测或生产数据。
- 数据库/Key：不修改，除非 R1-R4 已批准的具体变更需要。
- 兼容风险：压测仅在隔离环境进行。
- 测试：缓存命中、热点 Key、锁等待、Stream 吞吐/Pending、降级时数据库负载。
- 回滚：清理仅限隔离测试的显式前缀数据，由后续用户授权决定。
- 验收：简历仅陈述已实现且有测试/运行证据的能力；设计预留与待修复项明确排除。
