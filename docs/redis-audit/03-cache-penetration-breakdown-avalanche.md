# 03. 缓存穿透、击穿与雪崩审计

| 风险 | 当前证据 | 评价 | 建议 |
|---|---|---|---|
| 缓存穿透 | `CatalogCache` 对空对象/空列表写空标记，TTL 2 分钟；Controller DTO 有参数校验 | 商铺/商品/店铺商品列表已具备基础保护 | P2：验证码、全局列表、优惠券等没有缓存则不适用；先监控 404 回源频率，当前不引入 Bloom Filter |
| 缓存击穿 | 三类目录 Key 使用按实体粒度 Redisson 锁、双检、100ms 尝试、最多 3 次；失败会回源 | 有保护，但 10 秒显式租约小于不可证明的 DB P99 | P1：量化加载耗时；修正 lease/watchdog 策略前不能称击穿保护完全可靠 |
| 缓存雪崩 | 正常目录 TTL 加 0-5 分钟随机抖动；空值 TTL 固定 2 分钟；Redis 故障整体回源 | 常规目录已避免同一时刻失效；Redis 故障会让所有目录流量回 MySQL | P2：为 DB 回退设置连接/限流/告警；不在当前规模引入复杂预热集群 |
| 热 Key | 商铺详情、店铺商品列表、`qh:zset:explore:hot`、`qh:geo:shop` 与全局秒杀 Stream 是候选 | 只存在静态风险，未有命中/容量指标 | P2：增加命中、重建、ZSet/Stream 长度和慢命令指标后再定热点策略 |
| 大 Key | 每店全量商品 JSON、秒杀用户 Set、无裁剪 Stream、失败/重试 Hash | 真实无 TTL/无上限风险存在 | P1（秒杀/Stream）、P2（商品列表）：限制保留期、长度和业务上限 |

## 结论

- 商铺详情、商品详情和店铺商品列表已有空值缓存、随机 TTL 和互斥重建三项基础能力。
- 没有逻辑过期、请求合并、后台刷新和预热任务；当前不是缺陷，除非监控证明热点重建/数据库回退超标。
- Redis 整体不可用时的雪崩防护不足：目录模块选择安全回源，但没有应用级限流/熔断来保护 MySQL；秒杀则正确地快速失败。
